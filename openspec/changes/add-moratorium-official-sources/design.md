# Design

## Context

- The news workflow is generated by `moratorium-tracker/n8n/build_workflow.py`. This script builds every part of the workflow as module-level constants and writes the JSON when run. Its AI instructions (`SYSTEM_PROMPT`), Gemini request body and run-report style are what the new workflow should reuse. Importing the script today would run the whole build, because the file-writing code isn't guarded by `if __name__ == "__main__"`.
- The sheet (`Moratoriums` tab) has 15 columns and no row ID. n8n's Google Sheets node returns a `row_number` for each row it reads.
- The Gemini free tier allows a limited number of requests a day (the catch-up hit 429 and 503 errors). The news run already uses up to 60 calls every 2 days.
- Tested during exploration (21 Nov 2026):
  - Legistar `webapi.legistar.com/v1/{client}/matters` answers with no key; Charlotte (`charlottenc`) returned its moratorium matters.
  - Memphis, Loudoun, San Diego and Denton returned errors under the client names tried.
  - GovInfo search works with an api.data.gov key.
  - Open States v3 needs a key.

## Goals / Non-Goals

**Goals:**
- One new workflow that both finds actions and checks existing ones, sharing the AI instructions with the news workflow.
- Spend Gemini calls only on records that already pass a keyword filter.
- Make the watch-list and verification status something people can edit and audit in the sheet.

**Non-Goals:**
- Changing how the news workflow finds or classifies stories.
- Automatic discovery of Legistar client names. The watch-list is kept by people, with a one-off seeding pass.
- Agenda systems other than Legistar (CivicPlus, PrimeGov, BoardDocs).

## Decisions

**1. A separate workflow, not more steps in the news workflow.**
The sources, timing and failure modes are different, and a broken source must not stop the news run. It runs every 2 days at 09:00 Madrid time, two hours after the news run, so the two don't compete for Gemini quota or write to the sheet at the same time.
*Alternative:* add branches to the news workflow. Rejected because it makes one workflow longer and more fragile, and one run would then use twice the Gemini calls.

**2. Share code by importing it from the news build script.**
Guard `build_workflow.py`'s file-writing code with `if __name__ == "__main__"`. `build_official_sources.py` then imports `SYSTEM_PROMPT`, `GEMINI_BODY` and the sheet constants from it. Both scripts stay in `moratorium-tracker/n8n/`.
*Alternative:* a top-level `shared/` folder. Deferred until a second tracker exists, as agreed in exploration.

**3. Search each source, then filter by keywords, then use AI.**
```
 Config (window, caps)
   |-> Read watch-list --> Legistar matters per client (OData filter: intro date in window
   |                         AND title contains any of: data center, data centre,
   |                         data storage, datacenter)
   |-> Open States bills (q="data center" moratorium OR pause OR ban, updated in window)
   |-> GovInfo search (collection BILLS, "data center" moratorium, published in window)
   |      '-> Congress.gov bill actions (latest action as stage)
   v
 Normalise to {source, place, country, level, title, body, date, stage, url}
   v
 Keyword gate: title/body must also contain moratorium|pause|ban|prohibit|temporary|freeze
   v
 Gemini (same SYSTEM_PROMPT) -> confirmed actions
   v
 Match against sheet rows ---- match, row not person-verified --> UPDATE that row
                          '--- no match ----------------------> APPEND new row
   v
 Run report email
```
The keyword gate is what keeps Gemini usage small. Agenda items without a pause word (for example a utilities contract) never reach the AI.

**4. One matching rule for both finding and checking.**
A confirmed record matches a row when `country` and `jurisdiction` (after normalising case, "County"/"City of", and state codes) and `action_type` agree, and the row's `date_logged` or `effective_date` is within 120 days of the record date. One rule means a record found for the first time and a record that confirms an existing row go through the same code path. Ambiguous cases, where several rows match, update none and are listed in the run report.
*Alternative:* ask Gemini to compare each unverified row with each record. Rejected because the number of calls grows with rows × records.

**5. Update rows by `row_number`.**
Read the sheet once at the start of the run. Matched rows are updated through n8n's Google Sheets update operation, keyed on `row_number`. The update writes only `verified`, `verified_by`, `official_source_url` and `stage`, never other columns. Rows with `verified_by = person` are filtered out before matching.

**6. Public record links.**
`official_source_url` is the public page, not the API address. For example:
- Legistar: `https://{client}.legistar.com/LegislationDetail.aspx?ID={MatterId}&GUID={MatterGuid}`
- Federal bills: the congress.gov bill page
- State bills: Open States' page for the bill

**7. A watch-list tab instead of a list in code.**
The `Legistar watch-list` tab has the columns `jurisdiction`, `country`, `legistar_client`, `active`, `last_error` and `notes`. The workflow reads it at the start of each run and writes `last_error` back for places that failed. A one-off seeding task tries likely client names for the US places already in the sheet.

**8. Same catch-up controls as the news workflow.**
The Config node has `fromDate` / `toDate`, defaulting to the last 72 hours, and `maxItemsPerRun` for the Gemini step. Gemini calls give up after 30 s, with one retry for 5xx errors, and show Google's own error in the report.

## Risks / Trade-offs

- **Legistar client names are guesswork, and many councils don't use Legistar.** → The watch-list records failures in `last_error`. The README explains how to find a council's client name from its Legistar web address. Coverage is reported in the run email: places searched out of places listed.
- **Council wording varies** ("Data Storage Facilities", "hyperscale", "large load"). → The keyword list sits in the Config node, and the run report shows how many records each source returned before the gates.
- **A wrong automatic match marks a row verified.** → Requires agreement on place, action type and date window, plus AI confirmation. `verified_by = official` and `official_source_url` make every automatic decision checkable. A person can correct a row and set `verified_by = person`, which protects it from later runs.
- **Open States free-tier rate limits.** → One search request per run over all states, not one per state. The exact limits need confirming when the key is issued.
- **Updating by `row_number` while someone is editing the sheet.** → Rows can shift if a person inserts or deletes rows during a run. Runs are short and scheduled at 09:00 Madrid time. Before writing, the update step re-reads the row and checks that `headline` and `country` are unchanged.
- **Gemini quota shared with the news workflow.** → Runs are offset by 2 hours and the AI step has a cap. A run that hits quota reports it and leaves unchecked records for the next run, using the overlapping window.

## Migration Plan

1. Add the three columns to the end of the `Moratoriums` tab and create the `Legistar watch-list` tab. Existing rows keep `verified` as it is, with blank `verified_by`.
2. Import the new workflow with the Gemini, Google Sheets, Gmail, Open States and api.data.gov credentials, and run it by hand over one past week. Check every row it verified or added.
3. Run catch-up batches back to October 2026 to verify existing rows, then activate the schedule.
4. Roll back by deactivating the workflow. The new columns are harmless if left in place.

## Open Questions

- Which US places already in the sheet use Legistar, and under which client names. The seeding task answers this, and it doesn't change the design.
- The exact free-tier limits for Open States. They set the cap, not the approach.
